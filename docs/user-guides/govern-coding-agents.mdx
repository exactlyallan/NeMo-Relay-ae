Use a Relay daemon when developers should keep their coding harnesses while
your platform team owns their connection to providers and telemetry policy.
The daemon gives supported harnesses a managed entry point and starts a Relay
worker for each user-machine identity. The worker applies the approved plugins
to activity it observes; the developer continues in Claude Code, Codex, or pi.
A successful rollout produces an attributable, privacy-checked audit record for
representative model and tool activity from each supported path.

## Example: two users with a shared deployment

The companion uses one Linux host with two independent operating-system
accounts. **Alice runs Claude Code; Bob runs Codex CLI.** An administrator
installs the Relay CLI as a system daemon, provisions the managed harness
bundle, and owns the worker plugin configuration. Each user has a separate
home, route credential, provider authentication, task repository, and worker.

| Example participant | What runs there | Responsibility |
| --- | --- | --- |
| Administrator | Relay system service and immutable harness bundle | Distribute approved settings and plugin policy. |
| Alice | Claude Code, MCP lifecycle client, and Alice's worker | Complete a coding task using her provider credentials. |
| Bob | Codex CLI, MCP lifecycle client, and Bob's worker | Complete an independent task while Alice's session is active. |
| Receiving tier | Phoenix, or your chosen OTLP destination | Inspect supported model/tool activity and redacted synthetic data. |

<Note title="Example scope and alternatives">
This demonstrates a shared-host deployment with real separate Linux users.
Other supported coding harnesses and separate workstation deployments are
possible. Brev only supplies the host; use the same artifacts on a comparable
enterprise Linux host. Hermes uses a native in-process Relay integration and
is a different setup from these managed daemon clients.
</Note>

Require two distinct ready workers and inspect their process owners while both
sessions are open. Check the supported model and tool events in the receiving
tier, then close Alice's session and confirm Bob can continue. Relay identities
are routing identities; this example does not configure enterprise SSO or fleet
provisioning. Use the topology and acceptance decisions below for that rollout.

## Decide what the deployment must cover

The harness's provider request must pass through its Relay worker for model
telemetry or policy. Supported lifecycle hooks can add tool and session events,
but their coverage differs by harness. Inventory the harness and version, the
provider route it uses, the hooks you need, and the workstation operating system
before claiming organization-wide coverage. The
[coding-agent support matrix](/reference/support-matrix) gives the current
limits for Claude Code, Codex, and pi.

| Deployment | Where the daemon runs | Where the managed worker runs | Choose it when |
| --- | --- | --- | --- |
| Local | On each workstation | On that workstation under the user's identity | Local lifecycle and provider routing are acceptable. |
| Remote | On a trusted Linux server | On each client workstation under the user's identity | You need a centrally operated entry point and can provide a trusted server connection plus a return route to the client worker. |

In either topology, a worker uses administrator-owned system configuration and
managed harness settings. Users keep their normal provider login; a Relay route
credential identifies the user-machine session and must be unique to that
identity. The daemon does not turn an unsupported provider or hook path into a
captured one. See [daemon architecture](/daemon/architecture) for the trust and
network boundaries.

<Warning>
A provider response can succeed through pass-through while the managed worker
is absent. Decide whether pass-through is allowed for the cohort before rollout.
For a required audit boundary, accept a session only after the worker and its
plugin output are both visible.
</Warning>

Redaction applies to emitted observability data; it does not change the real
provider conversation. Test it with representative prompts and tool results
before sending production telemetry. If your audit pipeline collects ATOF
records instead of OTLP spans, configure that output under the same managed
policy. Keep collector credentials in the worker's secret-backed environment,
and avoid one writable log file shared by every worker.

For cost attribution, add a validated model-pricing catalog and confirm that
the observed response supplies model identity and token usage. Relay leaves
cost absent when it cannot estimate it; an absent value is missing coverage,
not zero spend. The [PII redaction](/configure-plugins/pii-redaction/configuration),
[Observability](/configure-plugins/observability/configuration), and
[model pricing](/configure-plugins/model-pricing) references provide the full
policy fields.

## Accept a workstation cohort

<Steps>
<Step title="Provision the managed identity and harness settings">
Distribute the administrator-owned configuration and harness artifacts. Give
each user-machine identity its own route credential, and confirm that the
harness actually targets its daemon entry point. For a remote deployment, also
confirm server trust and reachability back to the client worker.
</Step>

<Step title="Confirm worker-backed execution">
Start a non-sensitive session in each supported harness. Confirm the worker is
ready and bound to that session, then exercise one provider call and a harmless
supported tool hook. A ready MCP connection alone is insufficient: the worker
must receive the request, and an expected plugin result must appear.
</Step>

<Step title="Inspect the audit and privacy result">
Find the same session in the approved collector. Check the attributed identity
and service, agent/model/tool parentage where supported, model and token fields,
and redacted payloads. Record unsupported paths and any requests that bypassed
the worker before reporting fleet coverage or spend.
</Step>
</Steps>

| If the evidence is missing | Check first |
| --- | --- |
| No worker or plugin result | Managed bundle, route credential, worker readiness, and pass-through policy. |
| Model spans but no tool activity | Harness hook support and whether the tested action crosses a supported hook. |
| Trace present but cost absent | Model identity, usage fields, and the pricing catalog. |
| Unredacted sensitive field | The emitted surface and whether the configured detector covers it. |

The [managed-client configuration](/daemon/configuration) and
[worker-backed verification](/daemon/operations#verify-worker-backed-operation)
provide the platform-specific provisioning and operational checks. Repeat the
acceptance run after a policy, harness, or Relay upgrade.
